## Reference: how each HtmlSubwriter builds the itemNavForm now

As of this pass, `Html_MainWriter.Write_Body` calls exactly one method on the subwriter: `subwriter.Write_HTML(Output, Tracer)`. There is no more `Add_ItemNavForm_Content`/`Write_Final_HTML` call at that level, and no more `Include_Navigation_Form` gating in `Html_MainWriter` — each subwriter decides for itself, inline in its own `Write_HTML`, whether and when to open/close the `<form id="itemNavForm">` wrapper, using the protected `Write_ItemNavForm_Opening(Output)` / `Write_ItemNavForm_Closing(Output)` helpers on `abstractHtmlSubwriter`.

The following 8 classes had their formerly-separate `Write_HTML` / `Add_ItemNavForm_Content` / `Write_Final_HTML` methods merged into a single `Write_HTML`, with `// ===== Begin/End original ... =====` markers left in place wherever content came from more than one original method (so the merge history stays visible in-code): `Internal_HtmlSubwriter`, `Web_Content_HtmlSubwriter`, `MySobek_HtmlSubwriter`, `Admin_HtmlSubwriter`, `Search_Results_HtmlSubwriter`, `Public_Folder_HtmlSubwriter`, `Aggregation_HtmlSubwriter`, `Item_HtmlSubwriter`.

**`PagedResults_HtmlHelper` is the one exception, deliberately left un-merged.** It's a composed helper (never mode-dispatched, always addressed by concrete type — see `HtmlSubwriterFactory`, which doesn't create it), used by 4 different consumers: `Search_Results_HtmlSubwriter` and `Public_Folder_HtmlSubwriter` (both already merged, so they now call `writeResult.Write_HTML(...)` → `writeResult.Add_ItemNavForm_Content(...)` → `writeResult.Write_Final_HTML(...)` back-to-back inside their own single `Write_HTML`), plus `DataSet_Browse_Info_AggregationViewer` and `Folder_Mgmt_MySobekViewer` (different interface hierarchies, calling `Write_HTML` and `Add_ItemNavForm_Content` at genuinely separate rendering phases, not back-to-back). Because two of the four callers still need the methods independently callable, `PagedResults_HtmlHelper` keeps `Write_HTML` / `Add_ItemNavForm_Content` / `Write_Final_HTML` as three separate overrides — which is also why `abstractHtmlSubwriter` still declares `Add_ItemNavForm_Content`/`Write_Final_HTML` as virtual (base no-op) methods at all; nothing else overrides them anymore. (The `AggregationViewer` side of this same story — `Add_Secondary_Controls`/`Write_Within_ItemNavForm` — has since been resolved for the two viewers that needed it; see item 1 at top for the current state and why `PagedResults_HtmlHelper` itself still can't merge.)

**Every override in this area must carry the `override` keyword** — dispatch is purely virtual; a missing `override` silently falls back to the base no-op instead of erroring. This already bit `Item_HtmlSubwriter.Add_Main_Viewer_Section` once, before the original three-method split was removed.

Which `Display_Mode_Enum` modes actually get a `<form>` wrapper at all now comes down entirely to each subwriter's own `Write_HTML` logic (no more central gate) — check each class directly rather than relying on a table here, since that decision moved out of `Html_MainWriter`.
